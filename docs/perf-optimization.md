# 异步/协程库性能优化实录

> 本文记录 COM-Framework 对异步任务 / 协程库（`Common/Async` + `Common/Thread`）的
> 系统性性能优化过程：**方法、推理、被证伪的方案与最终结论**，而不仅是结果。
> 配套基准项目：`Benchmark/`（方法参考 asio / librf / Google Benchmark）。
>
> 所有结论均来自 `Benchmark/` 的前后对照实测 + 单元测试（64/64）验证。

---

## 1. 概述

对 **CThreadPool / CAsyncExecutor / CTask / CCoroutine** 做多轮优化，按"测量 → 假设 →
改造 → 对照 → 证伪/保留"循环推进。最终净效果（相对初始 baseline）：

| 指标 | 初始 | 最终 | 变化 |
|---|---|---|---|
| 单任务往返延迟 | ~25 μs | **~0.34 μs**（A1 后 337 ns） | **-99%** |
| 多生产者吞吐 | 0.8~1.9 M ops/s | **8~9.6 M ops/s** | **+5~10 倍** |
| 协程切换成本 | ~1004 ns | **~724 ns**（C9） | **-28%** |
| 协程 Get 路径（start+await+done） | ~25 μs | **~13 μs**（relaxed） | **-48%** |

并非所有尝试都成功：**一批"看起来更优"的方案被实测证伪并回退**（Then/协程无脑内联、
A2 批量消费、A4 work-stealing、B6 固定缓冲容器），证伪本身就是这套方法论的产出。

## 2. 被测对象与基线

| 对象 | 说明 |
|---|---|
| `CThreadPool` | 自研线程池：单全局任务队列 + 互斥锁 + 条件变量 |
| `CAsyncExecutor` / `CTask` / `CTaskState` | 无异常版异步任务框架（Option 风格，Then 链） |
| `CCoroutine` | Duff's device 无栈协程（CO_BEGIN/CO_AWAIT/CO_END 宏） |

**对比基线**：

- `direct_call`：理论下限（直接函数调用）；
- `asio`（项目自带 ThirdParty）：成熟第三方调度器；
- `std::thread`：最重的对照（每任务新建线程，仅作上界参考）。

## 3. 优化方法论（怎么优化）

### 3.1 测量优先：先把"尺子"做准

没有可靠的测量就没有优化。测量框架经历 4 轮改进（`1626dac` / `c5c685c` / `64e9130`）：

1. **消除测量污染**（`1626dac`）
   - `SubmitCase` 去掉 `std::promise`（内部 mutex + atomic 机制污染测量），改 **busy-wait
     原子计数**：单任务往返绝对值由 ~25 μs 降到 ~5-7 μs，三方引擎公平、更真实；
   - 采样 41→101（让 P99 可靠）、预热 8→20（让异步唤醒充分）。
2. **自适应迭代**（`c5c685c`，参考 Google Benchmark）
   - 固定采样改为"探测单次耗时 → 每轮自适应迭代（目标 ~2 ms）"，短/长操作都能统计充分；
   - 多轮采样（7 轮）取 **P50（中位数）为主指标**抗环境噪声，P90/P99 看长尾，stddev 看稳定性。
3. **鲁棒统计**（`64e9130`）
   - 引入 **MAD（中位数绝对偏差）离群值剔除**（阈值 3×MAD），均值/stddev 基于剔除后样本，
     MAD 列替代 stddev 列（更鲁棒）。
4. **正确性校验**（`64e9130`）
   - `SanityCheck`：计时前先验证结果（如 ChainCase 结果 =10、CoroutineCase =42/10），
     **防止"优化加速了错误代码"**。

### 3.2 证伪式优化：每个假设都要 A/B 对照

- 每次改动前后用 **stash / checkout 做真对照**，3 轮以上取均值，**确认无重叠**才下结论；
- 关键教训：**做对照前必须确认 stash/checkout 真实生效**（曾误用 stash 导致"合并前"数据
  实为"合并后"，结论差点作废）；
- 结论必须同时说明"为什么变快/变慢"，否则视为未完成。

### 3.3 延迟与吞吐是同一枚硬币的两面

- **延迟**（单任务往返）受"唤醒 + 投递"固定开销主导；
- **吞吐**（多生产者压力）受"并行度 / 负载均衡 / 竞争"主导；
- 两者往往互相排斥：内联续接省投递（降延迟）却破坏任务级并行度（降吞吐）。
  因此**必须同时测单线程微基准与多线程吞吐**，只测其一会被噪声或并行度问题误导。

### 3.4 测量陷阱清单（踩过的坑）

| 陷阱 | 后果 | 修正 |
|---|---|---|
| 主线程单线程提交压测 | 测的是 `Post` 速率而非线程池能力（4 线程仅 93K） | 新增 **4 提交线程多生产者用例**，暴露真实并行上限 |
| `std::promise` 混入 | 内部同步机制污染延迟 | 改 busy-wait 原子计数 |
| 只测单线程微基准 | 唤醒噪声主导，掩盖并行度问题 | 补多线程吞吐用例 |
| 样本/预热不足 | 异步唤醒未充分、P99 不可靠 | 预热 20+、样本 101+ |

## 4. 优化分组与结论

### 4.1 D 组：句柄与等待基础设施（"减固定开销"）

**D1 `Post`/`Submit` 句柄访问 —— 消除 refcount 竞争**（`69f6cf8`，**+10~15 倍**）

- 现象：多生产者压测中 `CAsyncExecutor`（130-210K）稳定落后底层 `CThreadPool`
  （0.8-1.9M）**5-8 倍**，说明瓶颈在执行器层而非线程池；
- 定位：`Post` 每次把局部 `shared_ptr` 拷贝进 lambda，在 4+ 提交线程下产生
  **原子 refcount 递增/递减的 cache line 竞争**；
- 方案：改用 `m_pHandle->`（`operator->` 不复制 `shared_ptr`），`Submit` 局部句柄改裸指针
  `m_pHandle.get()`，**保留 `task.m_pExecutor = m_pHandle` 的必要所有权转移**（任务链持有句柄保生命周期）；
- 结果：`CAsyncExecutor` 追平底层 `CThreadPool`（1.1-3.1M）。

**D2 `Wait` 自旋 —— 消除"睡→醒"futex 往返**（`8df5256`，**-38~60%**）

- 现象：短任务（μs 级）每次 `Get` 都走一次 futex 睡眠/唤醒，固定开销极大；
- 方案：`m_bReady` 原子化，`Wait()` 先自旋 50 μs（yield），超时未就绪再回退 condvar 阻塞；
- 结果：single task ~25→10 μs（-60%）、start+await+done ~25→14 μs（-45%）、chain x10 ~30→19 μs（-38%）。

**D3 `m_bReady` 改 relaxed —— 无 barrier 的原子**（`7e19c7e`，保留收益）

- 分析：`m_bReady` **唯一需要原子的访问是 `Wait` 锁外自旋**；其余访问全在锁内（锁已提供同步），
  atomic 冗余且默认 `seq_cst` 在弱内存序（ARM）上每次要 `dmb` 屏障；
- 方案：全部改 `memory_order_relaxed`——真正的同步由 `m_mutex` 保证，relaxed 编译为普通
  load/store，**开销等价普通 bool**；
- 结果：协程 Get 路径 start+await+done ~25→13 μs（**-48%**）。

### 4.2 B 组：续接合并（"减注册次数"）

**B5 合并续接 —— OnResult 一次注册**（`05641da`，**切换 -20%**）

- 现象：协程每级 await 的注册要 `OnSuccess` + `OnNone` **两次** `AddContinuation`；
- 方案：`CTask`/`CTask<void>` 新增 `OnResult(ResultCallback)`，一次注册接收最终 `CTaskResult`
  （有值/无值统一）；`RegisterTask`/`RegisterAllTask` 全部合并为一次；
- 结果：每级 await 省 **1 次续接 `std::function` 构造 + 1 次锁 push + 1 次回调调用**，
  switch x10000 ~1004→807 ns（-20%）。

**FlatMapForward 合并**（`3c8d6d3` + `7eb3194`，**flatMap -8%**）

- 与 B5 同思路，作用于任务框架的 flatMap 转发路径：由两次注册合并为一次 `OnResult`；
- `7eb3194` 新增 flatMap 链用例（checkout 到 51c0fab 对照）：x10 链 63.1→57.9 μs（-8.3%）。

**B6 固定缓冲续接容器 —— 权衡后回退**（`5bb7283`，后回退）

- 方案：`CFixedContinuation` 用 64B 内联缓冲替代 `std::function`（16B SBO 对捕获
  shared_ptr+指针+小状态 ~32B 必堆分配），4 函数指针类型擦除；
- 单线程微基准 -14~15%，但多线程中性；代价是 **+160 行复杂类型擦除代码**；
- 结论：**收益只体现在单线程微基准、维护成本高**，权衡后回退，续接回调保留 `std::function`。

### 4.3 C 组：协程内联与热路径（"减投递 / 减迁移"）

**无脑内联 —— 连续两次证伪**（`6c0669e` → `30c91c9` → `5afe778` → `67c6eb7`）

- 直觉：await 完成回调已在工作线程上，直接内联继续可省 1 次入队 + futex 唤醒；
- 首次测得吞吐 +26%（压力窗口 5000：88.2K→110.8K），**似乎成立**；
- 但补测 **Then 链内联**：多线程吞吐 42K→10K 条/s（**-76%**）；加大压力重测 10 级链
  30.5K→8.59K（**-72%**，确认非系统负载噪声）；
- 回查协程内联：多线程吞吐 385K→114K（**-70%**）——同样破坏并行度，**一并回退**；
- 根因：内联把"二次 Resume"合并进任务完成回调，**减少可调度单元、降低负载均衡**，
  以延迟换吞吐，在单队列线程池架构下得不偿失。

**C9 负载感知有界内联 —— 延迟/吞吐两全**（`b585f37`，切换 **-28%**，吞吐保持）

- 洞察：无脑内联失败在于"**无论负载都内联**"；关键变量是**线程池是否积压**；
- 方案：`CThreadPool` 新增原子 `m_nPending` 计数 + `PendingCount()`；`CAsyncExecutor` 新增
  `IsIdle()`（队列空）。`ResumeInline` **队列无积压时内联**（省投递、降延迟），**有积压时投递**
  （保并行度）；用 thread_local 深度计数限 64 层防爆栈；
- 结果（4 线程）：多线程协程吞吐 ~349K（无脑内联仅 114K，接近纯投递 385K）；
  切换 ~724 ns（纯投递 1004 ns，**-28%**）——两全其美。

**C10 热字段打包**（`51c0fab`，中性）

- 把协程三个热原子字段（step/terminated/reason）并入 `CHotState` 紧邻存放，减少跨线程迁移
  时需传递的 cache line 数；单实例原子无伪共享，属低风险结构优化；
- 实测与 C9 持平（无退化），作为结构性防御性优化保留。

### 4.4 A 组：线程池调度（"减唤醒 / 减竞争"）

**A1 混合等待 —— 单任务 -94%**（`fb6da6e`）

- 现象：单任务往返 5.97 μs，唤醒延迟主导；
- 方案：`WorkerLoop` 队列空且未停止时**先自旋 30 μs（读原子 pending，不持锁）**，任务刚提交
  时线程未睡可直接取，消除"睡→醒"futex 往返；超时再 condvar 阻塞；
- 结果：单任务往返 5.97 μs→337 ns（**-94%**）；多生产者 6.7M→6.5M（中性）。

**A3 通知优化 —— 多生产者 +26%**（`28bc601`）

- 方案：`Submit` 记录 `wasEmpty`，**队列非空时（线程在忙/自旋）不调用 `notify_one`**，
  批量提交省大量 futex 系统调用；
- 结果：多生产者 6.5M→8.2M ops/s（+26%，前两轮稳定 9.32M）；单任务 337→343 ns（持平）。

**A2 批量消费 —— 证伪回退**（`ffdff49`，**-95%**）

- 假设：一次取 16 个任务减少锁次数；
- 实测：8.2M→~400K（-95%）：**单线程独吞 batch 破坏 4 线程负载均衡** + batch vector 分配
  开销大于极短任务本身；
- 结论：批量消费对极短任务**反优化**；真实较长任务场景可另行评估小 batch。

**A4 work-stealing —— 证伪回退**（`4c46b20`，**-89%**）

- 假设：每线程队列 + round-robin 提交 + try_lock 窃取，减少全局锁竞争；
- 实测：8.1M→893K（-89%）：任务分散到 4 队列但 `notify_one` 只唤醒一个线程 → **其余队列积压**；
  窃取 `try_lock` 竞争 + 遍历开销大于单全局锁收益（极短任务场景）；
- 结论：**简化 work-stealing 不适用于极短任务多生产者场景**；成熟实现（TBB/folly 式）复杂度高，
  非当前收益-成本合理点。

## 5. 被证伪的方案（与成功同等重要）

| 方案 | 直觉 | 实测 | 根因 |
|---|---|---|---|
| Then 链内联 | 省投递 | **-72~76%** | 串行化破坏任务级并行度 |
| 协程无脑内联 | 省投递 | **-70%** | 同上 |
| A2 批量消费（batch=16） | 减少锁 | **-95%** | 单线程独吞 batch 破坏负载均衡 |
| A4 work-stealing（简化版） | 减少全局锁 | **-89%** | notify_one 只醒一个线程、窃取竞争 > 收益 |
| B6 固定缓冲容器 | 免堆分配 | 单线程 -14%，多线程中性 | 收益窄、维护成本高 → 权衡回退 |

> 共同教训：**"看起来更优"的简化方案在"极短任务 + 多生产者"场景下几乎都被证伪**。
> 调度器优化的收益/成本必须用真实负载形状（任务时长、并发度）验证，而非直觉。

## 6. 可复用优化技巧清单

**测量层**
1. 先校准"尺子"再优化；用 busy-wait 原子计数替代 promise 类测量污染源。
2. 单线程微基准（延迟）+ 多线程压力（吞吐）**必须都测**。
3. 多生产者用例要"多提交线程"（否则测的是提交速率）。
4. P50 为主、P90/P99 看长尾、MAD 剔除离群；多轮取均值，确认无重叠再下结论。
5. 每个用例带 SanityCheck，防止"加速了错误代码"。

**代码层（按性价比排序，均已实测）**
1. **消除共享指针无谓拷贝**（热路径 `shared_ptr` → `operator->`/裸指针）——往往收益最大。
2. **锁外自旋替代立刻睡眠**（WorkerLoop / Wait 两处）——极短任务下唤醒是最大固定开销。
3. **减少原子语义**：锁内访问用 `relaxed`，避免 `seq_cst` 的隐式屏障。
4. **合并回调注册**（两次 `AddContinuation` → 一次 `OnResult`）——省分配 + 锁 + 调用。
5. **只在"无积压"时内联**——用负载感知取代无脑内联，延迟/吞吐两全。
6. **减少 futex 系统调用**（队列非空时不 notify）。
7. **热字段打包**进同一 cache line（结构性防御，防伪共享/迁移）。

**决策层**
1. 收益按"真实负载下的吞吐/延迟"评估，而非单线程微基准。
2. 复杂度是成本：净收益不显著（如 B6）就回退，保持简单正确。
3. 记录每个证伪结论与根因——它们防未来重蹈覆辙。
