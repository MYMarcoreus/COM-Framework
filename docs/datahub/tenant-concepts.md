# 租户（Tenant）与多租户（Multi-tenancy）概念详解

> **本文档与具体项目无关**，讲的是通用概念。阅读顺序刻意安排为：**先讲"租户"和"单租户"，再讲多租户**——因为不理解单租户，就理解不了多租户在解决什么。
> 相关文档：[业界与其他项目实现](tenant-industry.md) · [本项目（DataHub）实现](tenant-project.md)

---

## 1. 先讲"租户"（Tenant）是什么

"租户"是**从租客/租户（Tenant）一词借来的软件概念**：软件供应商把一套系统"租"给客户，客户就是"租户"。

广义定义：

> **租户 = 一套软件服务所服务的"一个客户/组织/部署单元"**。它为这个客户承载独立的数据、配置与使用边界。

这里的关键是：**即使一个系统只为一个客户服务，它依然可以有"租户"**——只是只有一个租户而已。换句话说，租户是"客户边界"的概念，和"是否多个客户共用"无关。

## 2. 单租户（Single-tenancy）概念

**单租户** = **一套部署只服务一个客户（组织）**，客户之间物理隔离——不同客户用完全不同的部署/实例/数据库。

```text
客户 A ──> 部署 A（自己的机器/容器/数据库）
客户 B ──> 部署 B（自己的机器/容器/数据库）
客户 C ──> 部署 C（自己的机器/容器/数据库）
```

### 2.1 单租户的特点

| 维度 | 单租户表现 |
|---|---|
| 隔离 | 最强：物理/资源级隔离，天然无串扰 |
| 定制 | 最容易：每个客户可单独改版本/参数 |
| 合规 | 最省心：客户数据不出自己实例，满足苛刻合规 |
| 成本 | 最高：N 个客户 = N 份资源与运维 |
| 升级/运维 | 最重：要逐套打补丁、升级、监控 |
| 规模 | 难放量：每新增客户都要开新实例 |

### 2.2 典型形态

- **企业软件私有化部署**（ERP/CRM 卖给一家大企业，装到对方机房）；
- **专享实例/专属集群**（SaaS 厂商给 VIP 客户单独开的实例，也叫 single-tenant tier）；
- 云上"每客户一个账号"的强隔离（如企业按云账号隔离资源）。

### 2.3 适用场景与局限

适用：大客户、强合规、高定制、单价高。
局限：成本随客户线性上涨、运维繁重、难以服务海量中小客户——于是有了**多租户**。

## 3. 为什么从单租户走向多租户

| 单租户痛点 | 多租户的解法 |
|---|---|
| N 客户 = N 部署，成本线性涨 | **一套部署服务所有客户**，摊薄成本 |
| 升级/运维繁重 | 一处升级，人人受益 |
| 难服务海量中小客户 | 低单价也能赚钱（SaaS 起量的基础） |
| 资源利用率低 | 共享计算与存储，提高利用率 |

> 注意：**多租户并不是取代单租户**。业界常是"混合部署"：默认多租户快速起量，高价值客户升级到"专享实例/单租户 tier"。二选一不如看成一条频谱。

```text
强隔离/高成本                       共享/低成本
单租户实例  <- 数据库每租户 <- schema每租户 <- 共享表+tenant_id -> 海量SaaS
```

## 4. 多租户（Multi-tenancy）概念

**多租户** = **同一套软件/同一份部署，同时服务多个相互隔离的租户**。租户之间互不可见（数据、成员、配置），但共享计算与运维。

几个容易混的词：

| 词 | 含义 |
|---|---|
| **租户（Tenant）** | 隔离单元 = 一个客户组织/团队/工作区 |
| **账号（Account / User）** | 一个登录主体；**账号可属于多个租户**（一个人在不同公司） |
| **成员资格（Membership）** | "某账号在某租户内"这件事，带角色（所有者/管理员/成员） |

> 业界叫法很多、意思相同：Org（GitHub）、Workspace（Slack）、Site（Atlassian）、Space/Team（飞书/Notion）、Enterprise（企微/钉钉）、Account/Tenant（云厂商）。

## 5. 多租户隔离发生在哪些维度

新手以为"多租户 = 数据库加个字段"。其实隔离散落在每一层：

- **数据**（最核心）：库/表/行级隔离；
- **缓存**：Redis key 不加租户前缀会串租户；
- **对象存储/文件**：路径带租户前缀（否则 `GET /file/{id}` 换租户可读）；
- **任务/队列**：后台任务必须携带租户上下文（否则批处理把 A 的写进 B）；
- **日志/指标**：按租户打标签（排查与计量）；
- **配置/配额/计费**：每租户一套；
- **密钥/白标/域名**：每租户独立。

## 6. 三类数据隔离模型

| 模型 | 做法 | 隔离 | 成本 | 单租户可扩展 | 适用 |
|---|---|---|---|---|---|
| **Database-per-tenant** | 每租户一个数据库 | 最强 | 最高 | 强 | 大客户、合规强（≈单租户思路） |
| **Schema-per-tenant** | 共享数据库、每租户一个 schema | 强 | 中 | 中 | 中型、隔离与成本折中 |
| **Shared table + tenant_id** | 一张表，每行带租户列 | 逻辑隔离 | 最低 | 弱（单表膨胀） | 海量小租户、SaaS 起步 |

**不是"选一个就完"**，业界常**演进 + 混合**：先 shared table 起量 → 大租户迁 schema/db（按租户路由）。

**Shared-table 的关键**：所有查询**必须强制 `WHERE tenant_id = ?`**，靠"约定 + 拦截"两层保证；任何漏掉的地方就是数据泄漏（见第 8 节）。

> 与单租户的关系：`Database-per-tenant` 就是"多租户版的单租户隔离"——资源仍共享管理，但每个租户的数据独立成库。

## 7. 应用层如何"感知租户"

1. **解析租户标识**：子域名（`acme.app.com`）、请求头、JWT/会话里的租户声明、路径前缀；
2. **放进请求/线程上下文**（TenantContext / ThreadLocal / Context）——一次请求内全局可读；
3. **传给数据访问层并强制拼接谓词**：不在 Controller 手拼（会漏），在**数据层/ORM/中间件统一注入**；
4. 进阶：数据库**行级安全（RLS）**——SQL 忘写租户条件也由 DB 按当前租户过滤，**双保险**；
5. 缓存/文件/任务同理会话级注入租户。

## 8. 常见反模式与攻击面（重点考点）

| 反模式/漏洞 | 现象 | 防护 |
|---|---|---|
| **IDOR / 换租户越权（BOLA）** | 传 `id` 不校验归属，改租户 id 就读到别人数据（OWASP API Top1 类别） | 数据层强制租户谓词；"租户内查找"，跨租户即 not-found |
| 漏 `tenant_id` 过滤 | 聚合/统计/后台任务忘拼条件 | 统一拦截 + 行级安全兜底 |
| **缓存串租户** | key 不带租户 | key/namespace 加租户前缀 |
| 信任前端传的租户 id | 直接用请求体里的租户 id | 从登录态/JWT 解析，不信任请求体 |
| 后台任务无租户上下文 | 批处理张冠李戴 | 任务携带租户上下文 |
| 只看存储不做边界 | 聊天/推送跨租户串 | presence/推送按租户订阅 |

## 9. 组织 / 账号 / 成员 / 角色（RBAC）

常见误区：把"账号"当"租户"。正确建模是三层：

```text
账号（User，全局唯一）
   └─ 成员资格（在哪些租户、什么角色）
         ├─ Owner   拥有者：管理租户/成员/数据
         ├─ Admin   管理员：成员与配置
         └─ Member  成员：日常使用
租户（Org/Workspace）
   ├─ 数据 / 配额 / 设置
   └─ 成员表 membership(tenant_id, user_id, role)
```

租户级"邀请/加入"（凭邀请码/链接）与"踢出/退出"是组织软件的基本闭环。角色决定权限：Owner 可删任意、可管成员；Member 只能用自己的。

## 10. 租户级功能（不止隔离）

成熟 SaaS 对租户做：**配额与计量**（条数/容量/带宽/并发）、**计费套餐**、**每租户配置/白标**、**审计日志**、**按租户的监控告警**。

## 11. 小结：单租户 vs 多租户怎么选

| | 单租户 | 多租户 |
|---|---|---|
| 隔离 | 物理级 | 逻辑级为主 |
| 成本 | 高 | 低 |
| 定制/合规 | 强 | 靠设计补偿 |
| 放量 | 难 | 易 |
| 典型 | 私有化、VIP 专享 | SaaS |

**选择建议**：中小客户、要快速放量、单价低 → 多租户起步；大客户、强合规/高定制 → 单租户或升级专享实例；成熟企业常**两者混合**。

### 通用速记（单租户也适用）

1. 租户 id（或实例 id）用不可变标识，数据只引用它、不按名字快照；
2. 查询强制租户/实例谓词 +（有条件时）行级安全双保险；
3. 跨层（缓存/文件/队列/日志）统一带租户键；
4. 账号 ≠ 租户：membership + role 第三层建模；
5. 交互先"选/建组织"，组织内协作；
6. 被踢/解散要给用户明确事件与离场，不是悄悄 404；
7. 控制面与数据面分离，租户可运营（配额/计费/审计）。
